# ДомДело

«ДомДело» превращает неформальное сообщение в домовом чате MAX в одно коллективное дело: проблема → подтверждения соседей → назначение → работа → фото результата → проверка жильцами.

Это первый рабочий срез MVP. В нём уже доступны сквозной сценарий мини-приложения, API, PostgreSQL-модель, дедупликация, workflow, загрузка фото, outbox и защищённый webhook. Бот проводит жильца через описание и фотографию, показывает найденный дубль и по выбору присоединяет сообщение к существующему делу либо создаёт отдельное.

## Быстрый запуск через Docker

Требуются Docker Engine/Desktop и Compose.

1. Скопируйте `.env.example` в `.env`.
2. Заполните как минимум `POSTGRES_PASSWORD`, `S3_SECRET_ACCESS_KEY` и `SESSION_SECRET` случайными значениями.
3. Выполните:

```bash
docker compose up --build
```

Мини-приложение: `http://localhost:8080`  
OpenAPI UI: `http://localhost:8080/docs`  
Health: `http://localhost:8080/health/ready`

Compose при старте применяет миграции и загружает синтетические демонстрационные данные. Для остановки без удаления данных выполните `docker compose down`; повторный `docker compose up --build` использует те же volumes. Удалить тестовую базу и файлы можно только отдельной командой `docker compose down -v`.

Перед первым запуском создайте `.env` из `.env.example` и задайте случайные значения `POSTGRES_PASSWORD`, `S3_SECRET_ACCESS_KEY` и `SESSION_SECRET`. Не используйте рабочие секреты в локальном демо. Переменные и их назначение перечислены ниже.

## Локальный demo-режим без Docker

Поддерживается Node.js `>=24.19.0 <25` и pnpm `11.25.0`. Рекомендуемая версия Node.js — `24.21.0` (закреплена в `.nvmrc` и Dockerfile).

```bash
pnpm install --frozen-lockfile
pnpm build:packages
```

В первом терминале:

```powershell
$env:STORAGE_MODE='memory'
$env:DEMO_MODE='true'
$env:MAX_WEBHOOK_SECRET='local-test-secret'
$env:SESSION_SECRET='local-development-session-secret'
pnpm dev:server
```

Во втором:

```bash
pnpm dev:web
```

Откройте `http://localhost:5173`. В верхней панели можно переключать вымышленные роли жильца, диспетчера и исполнителя.

## Расширение функций дома

Требования по десяти направлениям, реализованный демо-срез, источники данных, роли и ограничения интеграций: [docs/gosuslugi-dom-roadmap.md](docs/gosuslugi-dom-roadmap.md). В текущем срезе диспетчер может указать плановую дату выполнения, а житель видит её и историю этапов в карточке. Эта дата — прогноз, не официальный нормативный срок.

## Основной сценарий

1. При первом входе житель обязательно добавляет адрес дома. До этого список дел и остальные действия недоступны.
2. Пользователь может добавить несколько домов в «Мои адреса» и выбрать активный дом.
3. Житель нажимает «Создать дело», описывает проблему и прикладывает фотографию в MAX либо делает это в мини-приложении.
4. В мини-приложении кнопка «Проверить и продолжить» сразу создаёт дело в активном доме и показывает сообщение об успешном размещении.
5. В диалоге с ботом поиск похожих открытых дел предлагает присоединиться к совпадению либо создать отдельное дело. В мини-приложении к существующему делу можно присоединиться кнопкой «У меня тоже» в его карточке.
6. До отправки диспетчеру дело собирает подтверждения от `max(2, ceil(число зарегистрированных аккаунтов дома / 10))` разных пользователей. Автор считается первым. В карточке видны прогресс и недостающее число подтверждений; отдельной автоматической отправки срочных или аварийных дел нет. При достижении порога дело один раз попадает в демонстрационную очередь УК, а карточка показывает успех отправки. Затем диспетчер назначает исполнителя и меняет статусы только по разрешённому графу.
7. Исполнитель добавляет фото результата.
8. Житель подтверждает результат либо оспаривает его.

Адрес выбирается из подсказок и повторно проверяется сервером. В локальном демо без DADATA_API_KEY доступен только явно помеченный вымышленный дом. Проверка адреса не подтверждает право проживания или собственности; в рабочем режиме карточки настоящего дома закрыты до записи подтверждённого полномочия на сервере. Для хакатонного показа на Render доступен отдельный вымышленный дом с пометкой «Демо»: его можно открыть без проверки прав, но он не выдаёт доступ к данным настоящих домов.

Жилец добавляет адрес и получает доступ к делам без кода. Служебные роли диспетчера и исполнителя выдаются по личному приглашению после проверки полномочий. Адрес можно удалить из профиля. Подробности: [docs/registration.md](docs/registration.md).

Подробная проверка: [docs/testing-scenario.md](docs/testing-scenario.md).

## Архитектура

Модульный монолит на TypeScript:

- Fastify + официальный `@maxhub/max-bot-api`;
- React + Vite + MAX UI + TanStack Query;
- PostgreSQL 17.11 + Drizzle + `pg_trgm`;
- S3-совместимое хранилище, MinIO только для локального demo-контура;
- outbox worker без Redis;
- Nginx reverse proxy и единый Dockerfile с targets `server`/`web`.

Подробнее: [docs/architecture.md](docs/architecture.md).

## Зависимости, окружение и порты

Для локального запуска всего контура нужны Docker Engine/Desktop с Docker Compose. Dockerfile закрепляет Node.js `24.21.0`, pnpm `11.25.0` и production-зависимости; точные версии библиотек зафиксированы в `pnpm-lock.yaml`. Для запуска без Docker нужны Node.js `>=24.19.0 <25` и pnpm `11.25.0`.

| Порт | Доступность | Назначение |
|---|---|---|
| `8080` | хост | Веб-приложение, API, webhook и `/docs` через Nginx |
| `3000` | только сеть Compose; при dev-запуске доступен локально | Backend API и бот |
| `5432` | только сеть Compose | PostgreSQL |
| `9000`, `9001` | только сеть Compose | S3 API и консоль MinIO |
| `5173` | хост, только `pnpm dev:web` | Vite dev-сервер мини-приложения |

Переменные берутся из `.env.example`. Для Compose обязательны:

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD` | Пароль локальной PostgreSQL и соединения приложения с ней |
| `S3_SECRET_ACCESS_KEY` | Секрет локального MinIO |
| `SESSION_SECRET` | Подпись сессий приложения |

В `.env.example` перечислены все параметры окружения: `NODE_ENV`, `PORT`, `PUBLIC_BASE_URL`, `MAX_MINI_APP_URL`, `MAX_MINI_APP_BOT_USERNAME`, `DATABASE_URL`, `POSTGRES_PASSWORD`, `MAX_API_BASE_URL`, `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `DADATA_API_KEY`, `MAX_DELIVERY_MODE`, `MAX_POLLING_REMOVE_WEBHOOKS`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE`, `SESSION_SECRET`, `LOG_LEVEL`, `DEMO_MODE`, `STORAGE_MODE`, `OBJECT_STORAGE_MODE`, `SERVE_WEB`, `HACKATHON_HOUSE_ID` и `HACKATHON_HOUSE_ADDRESS`. Для настоящего бота задайте `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, публичный HTTPS `PUBLIC_BASE_URL`, HTTPS `MAX_MINI_APP_URL` и `MAX_MINI_APP_BOT_USERNAME`. Для поиска новых реальных адресов на hosted-стенде нужен `DADATA_API_KEY`; локальный Compose использует синтетический seed и сервисы PostgreSQL/MinIO по внутренним именам `postgres` и `minio`. Compose также читает `DATABASE_URL`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_FORCE_PATH_STYLE`, `MAX_API_BASE_URL`, `MAX_DELIVERY_MODE`, `LOG_LEVEL`, `DEMO_MODE` и `STORAGE_MODE`. `MAX_POLLING_REMOVE_WEBHOOKS`, `OBJECT_STORAGE_MODE`, `SERVE_WEB`, `HACKATHON_HOUSE_ID` и `HACKATHON_HOUSE_ADDRESS` нужны для соответствующих polling, hosted или демонстрационных режимов. Секреты не передаются во frontend; не заполняйте рабочими значениями `.env.example` и не коммитьте `.env`.

## Внешние сервисы и данные

Для обработки реальных сообщений MAX необходимы бот, выданный MAX токен, webhook на публичном HTTPS-адресе и привязка Mini App к тому же боту. Для локальной проверки внутри MAX используется `pnpm dev:max` и временный HTTPS-туннель; это не постоянный адрес и не production-стенд. DaData используется только для подсказок адресов и серверной проверки кода дома по ГАР. Локальный контур хранит фото в MinIO, а hosted-конфигурация может использовать S3-совместимое хранилище либо небольшие фотографии в PostgreSQL.

Интеграций с реальными УК, ГИС ЖКХ и муниципальными системами нет: передача в очередь УК в MVP является внутренним демонстрационным действием. Начальные дома, учетные записи и дела синтетические; при старте Compose они загружаются seed-скриптом в PostgreSQL. Не используйте в демодоме реальные персональные данные или документы. После перезапуска контейнеров записи и фотографии сохраняются в именованных volumes. Подробнее о ролях, источниках данных и ограничениях: [docs/registration.md](docs/registration.md) и [docs/architecture.md](docs/architecture.md).

## Конфигурация MAX

1. Создайте бота и передайте токен только через `MAX_BOT_TOKEN`.
2. Задайте `MAX_WEBHOOK_SECRET` длиной 5–256 символов (`A-Z`, `a-z`, `0-9`, `_`, `-`).
3. Разместите стенд на публичном HTTPS-домене с доверенным сертификатом и портом 443.
4. Создайте подписку `POST https://platform-api2.max.ru/subscriptions` на `${PUBLIC_BASE_URL}/webhooks/max`.
5. Мини-приложение подключите к тому же боту. Frontend передаёт только `window.WebApp.initData`; `MAX_BOT_TOKEN` во frontend не попадает.

### Запуск локального мини-приложения внутри MAX

MAX не открывает `http://localhost` как Mini App: платформа принимает только HTTPS. Для
локальной разработки проект автоматически оставляет приложение на вашем компьютере и
публикует его через временный HTTPS-туннель на обычном исходящем порту 443.

1. Добавьте `MAX_BOT_TOKEN` тестового бота в локальный `.env`.
2. Выполните:

```powershell
pnpm dev:max
```

Команда собирает общие пакеты, запускает frontend и API, получает временный HTTPS-адрес,
добавляет его в обычную кнопку-ссылку и включает Long Polling. По умолчанию используется
Pinggy, а Cloudflare Quick Tunnel остаётся резервным вариантом. Произвольный URL нельзя
передать в `open_app`: поле `web_app` содержит username бота, чьё приложение уже
зарегистрировано на платформе MAX.
После сообщения «ДомДело готово» отправьте боту `/start` и нажмите «Открыть ДомДело».
В локальном режиме ссылка откроется во внешнем браузере.
Остановка всех локальных процессов — `Ctrl+C`.

Бесплатный туннель предназначен только для разработки: его адрес меняется при запуске,
сессия может быть ограничена по времени, а данные demo-режима хранятся в памяти.
Используйте отдельного тестового бота. Если у бота
есть webhook-подписки, запуск по умолчанию остановится, не удаляя их. Только для осознанного
переключения этого же бота на polling задайте `MAX_POLLING_REMOVE_WEBHOOKS=true`; после теста
production webhook придётся создать заново.

### Постоянный сервер

Для production укажите стабильные адреса:

```dotenv
PUBLIC_BASE_URL=https://domdelo.example.ru
MAX_MINI_APP_URL=https://domdelo.example.ru
MAX_MINI_APP_BOT_USERNAME=domdelo_bot
MAX_DELIVERY_MODE=webhook
```

`PUBLIC_BASE_URL` используется для API и webhook, `MAX_MINI_APP_URL` — для обычных ссылок,
а `MAX_MINI_APP_BOT_USERNAME` включает встроенную кнопку `open_app`. Если frontend и API размещены на разных доменах, домен Mini App всё равно должен
проксировать относительные пути `/api` на backend. При пустом `MAX_MINI_APP_URL` проект
автоматически использует `PUBLIC_BASE_URL`, но только когда тот начинается с `https://`.

Стабильный `MAX_MINI_APP_URL` нужно один раз указать в настройках этого бота на
платформе MAX для партнёров — тогда у чата появится постоянная системная кнопка запуска.
Inline-кнопки `/start` и «Открыть карточку» бот отправляет сам; карточка открывается через
безопасный стартовый параметр `case_<uuid>`.

### Хакатонный стенд на Render

В корне репозитория есть [`render.yaml`](render.yaml): один Web Service отдаёт сайт, API и webhook
с одного постоянного HTTPS-адреса `*.onrender.com`, а PostgreSQL хранит заявки и небольшие
демонстрационные фотографии. В Render откройте **New → Blueprint**, выберите этот репозиторий
и ветку с `render.yaml`. При создании укажите `MAX_BOT_TOKEN` и придумайте отдельный
`MAX_WEBHOOK_SECRET` из 32–64 латинских букв и цифр. Токен нельзя помещать в Git или
передавать браузерному коду.

После состояния **Live** скопируйте адрес Web Service. Его нужно указать в настройках
этого бота на платформе MAX для партнёров как URL мини-приложения. Для сообщений бота
создайте подписку MAX на `https://<адрес>/webhooks/max` с тем же `MAX_WEBHOOK_SECRET`.
Когда Mini App уже привязан, можно дополнительно задать `MAX_MINI_APP_BOT_USERNAME` в
Render: бот начнёт отправлять встроенную кнопку `open_app` вместо обычной ссылки.

Для подсказок и проверки домов зарегистрируйте ключ API DaData и добавьте его в Render
как переменную окружения `DADATA_API_KEY` (не в Git и не во frontend). Новые адреса
сохраняются только после выбора дома из подсказок и повторной проверки его кода ГАР
на сервере. Если ключ не задан или DaData недоступна, добавление нового адреса
останавливается с понятной ошибкой; ранее сохранённые дома и дела продолжают работать.
После добавления ключа перезапустите сервис или дождитесь нового деплоя.

Стенд использует один **демонстрационный дом** (`HACKATHON_HOUSE_ID`): пользователь
входит со своей подписанной учётной записью MAX и открывает его отдельной кнопкой. Дела этого
дома общие, но действия пользователей учитываются отдельно. Внутри вымышленного дома можно переключить демонстрационную роль, включая председателя,
диспетчера и госорган. Она не действует в настоящих домах и не подтверждает полномочия.
Все дела демодома доступны участникам показа: не указывайте настоящие имена, номера квартир,
контакты и не прикрепляйте личные документы.

Сценарий показа: в чате MAX отправьте `/start`, нажмите **Демо-режим**, затем выберите
роль. В мини-приложении нажмите **Показать сценарий** — приложение само выберет
демонстрационный дом и откроет нужный раздел. Сменить роль можно через плашку
деморежима; если реальный адрес уже добавлен, вход в демо также есть в **Мои дома**.
После показа выберите реальный дом в переключателе адресов. Роли в демодоме не дают
прав в реальных домах. Сведения об УК и капремонте в демодоме — вымышленные и
отмечены как учебный пример; загрузка произвольных фото в общем демодоме отключена,
а полноэкранный просмотр показывается на учебной иллюстрации.

Бесплатный Render засыпает после 15 минут без запросов, а бесплатная база PostgreSQL
действует 30 дней и не имеет резервных копий. Перед показом разбудите стенд открытием
его URL; для надёжного постоянного сервиса потребуется другой тариф или хостинг.

Корневой сертификат Минцифры для подключения к MAX хранится локально в
`infra/certs/russian_trusted_root_ca.cer`; источник — официальный ресурс Госуслуг
`https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer`.

Актуальность MAX API проверена 24.09.2026: используется `platform-api2.max.ru`, `open_app.web_app` содержит username или ссылку на бота с зарегистрированным Mini App, webhook использует заголовок `X-Max-Bot-Api-Secret`.

### Пошаговая проверка и ожидаемый результат

1. Скопируйте `.env.example` в `.env`, задайте три обязательных локальных секрета и запустите весь локальный контур одной командой: `docker compose up --build`.
2. Дождитесь готовности сервисов, откройте `http://localhost:8080` и пройдите основной сценарий из [docs/testing-scenario.md](docs/testing-scenario.md). Для проверки полного чатового потока в MAX следуйте разделу «Локальный запуск мини-приложения внутри MAX» выше.
3. В синтетическом доме житель создаёт дело с описанием и фото. При достижении порога подтверждений разных пользователей дело появляется во внутренней очереди диспетчера; повторное подтверждение тем же аккаунтом счётчик не увеличивает. Диспетчер назначает исполнителя и меняет статусы по графу, исполнитель прикладывает фото результата, житель подтверждает результат или оспаривает его.
4. Для устойчивости повторите webhook-событие и запрос создания дела с теми же идентификаторами: дубль не должен создаваться. Ошибочное изменение статуса отклоняется, а после временной ошибки пользователь может повторить действие. Весь расширенный список шагов и ожидаемых ответов приведён в [docs/testing-scenario.md](docs/testing-scenario.md).

Остановка выполняется через `docker compose down`, повторный запуск — снова `docker compose up --build`. Команда с `-v` удаляет демо-данные и нужна только для полного сброса локального стенда.

## Безопасность и данные

- Рабочие секреты не хранятся в репозитории; `.env` игнорируется.
- `initData` проверяется сервером через HMAC-SHA256 и срок выдачи.
- Роль и дом берутся из серверной сессии.
- Создание дела защищено `Idempotency-Key`, webhook — таблицей обработанных событий, смена статуса — `expectedVersion`.
- Фото ограничены JPEG/PNG/WebP и 8 МБ; S3-ссылки имеют ограниченный срок.
- Перед созданием дела и сменой статуса сервер проверяет свободный текст на нецензурную лексику; отклонённый текст не сохраняется и не рассылается. Проверка работает локально без внешнего API.
- Контейнер приложения запускается от пользователя `node`, web — на unprivileged Nginx.
- В seed нет реальных персональных данных; все сущности помечены `is_demo=true`.

## Известные ограничения

- Словарная проверка текста может пропустить новые обходы или ошибочно отклонить слово; содержимое фотографий и надписи на них не проверяются.
- Для реальной проверки production MAX нужны токен организаторов, стабильный HTTPS-стенд и привязка Mini App в настройках бота; Quick Tunnel подтверждает только локальный тестовый контур.
- На машине разработки Docker отсутствует, поэтому clean-clone Compose-запуск ещё необходимо проверить в среде с Docker.
- Незавершённый пошаговый диалог бота хранится в памяти одного процесса и сбрасывается при перезапуске; зарегистрированные дела и фотографии хранятся в PostgreSQL/S3. До горизонтального масштабирования черновики нужно перенести в PostgreSQL.
- MinIO community upstream архивирован; в локальном контуре сохранён требуемый стек, но перед production-пилотом нужен поддерживаемый S3-вариант.
- Реальные интеграции с УК, ГИС ЖКХ и муниципальными системами не входят в MVP и не имитируются.

Порог пересчитывается по текущим регистрациям в доме до отправки; после отправки порог и время фиксируются. Контрольный таймер работы УК начинается при попадании дела в очередь. Миграция `0010_case_confirmation_gate.sql` возвращает ранее зарегистрированные дела без достаточных подтверждений в сбор подтверждений; уже принятые в работу дела сохраняют историю. Новая отправка означает только внутреннюю демонстрационную очередь, без интеграции с настоящей УК.
