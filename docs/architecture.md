# Архитектура MVP «ДомДело»

## Цель первого среза

Первый срез закрывает один вертикальный сценарий: житель регистрирует проблему, система показывает похожее открытое дело, диспетчер проводит дело по допустимым статусам, исполнитель добавляет фотографию результата, а житель подтверждает или оспаривает работу.

## Состав

```text
MAX bot / MAX mini-app
          |
          v
      Nginx :8080
       |       |
       |       +--> React + MAX UI
       v
  Fastify modular monolith
       |          |            |
       v          v            v
  PostgreSQL   S3/MinIO     MAX Bot API
  + outbox     фотографии   уведомления
```

- `apps/server` — webhook MAX, REST API, предметные сервисы и outbox worker.
- `apps/web` — единое React-мини-приложение для жильца, диспетчера и исполнителя.
- `packages/domain` — конечная модель состояний и правила переходов.
- `packages/contracts` — общие runtime-схемы и TypeScript-типы API.
- `packages/config` — централизованная типизированная конфигурация.
- `db/migrations` — SQL-миграции Drizzle, включая `pg_trgm`.
- `db/seeds`/`apps/server/src/db/seed.ts` — явно помеченный демонстрационный дом.

## Границы модулей

| Модуль | Ответственность |
|---|---|
| `auth` | проверка подписи и возраста `window.WebApp.initData`, серверная сессия, demo-роли |
| `houses` | обязательный адресный онбординг, избранные дома и выбор активного адреса |
| `cases` | список, карточка, регистрация, подтверждение и наблюдение |
| `case-workflow` | роль, допустимый переход, optimistic locking, история, аудит и outbox |
| `deduplication` | дом + категория + подъезд + 30 дней + `pg_trgm`, максимум три кандидата |
| `routing` | детерминированное правило предполагаемого ответственного |
| `attachments` | JPEG/PNG/WebP до 8 МБ, S3-объект и временная подписанная ссылка |
| `bot-conversation` | пошаговый сбор описания и фото, объяснимый разбор полей, предложение объединить дубль |
| `notifications` | outbox с повторными попытками и отправка в MAX официальным клиентом |
| `audit` | неизменяемые записи значимых действий |

## Инварианты

1. Статус нельзя обновить прямым SQL из HTTP-обработчика: используется один workflow-сервис/репозиторий.
2. Смена статуса, история, audit и outbox записываются в одной транзакции PostgreSQL.
3. `expectedVersion` предотвращает потерю параллельного изменения карточки.
4. `Idempotency-Key` предотвращает повторное создание дела при повторе запроса.
5. `processed_webhook_events` предотвращает повторную обработку webhook MAX.
6. Роль и дом берутся из проверенной серверной сессии; URL не является источником полномочий.
7. Рабочие секреты не входят в исходный код и не отправляются во frontend.
8. До добавления первого адреса API дел возвращает `address_required`; все запросы дел ограничены активным избранным домом пользователя.

Незавершённый диалог бота пока является короткоживущим состоянием процесса. Все завершённые действия проходят через общий репозиторий и сохраняются в PostgreSQL; перед запуском нескольких экземпляров приложения черновики диалога нужно вынести в PostgreSQL.

## Данные и честность демонстрации

Seed содержит только вымышленные имена и адрес. Поля `is_demo` и видимый маркер «Демо-данные» отделяют моделируемый дом от реального подключения. Интеграции с ГИС ЖКХ, УК и муниципальными системами не имитируются: в MVP используется тестовый диспетчер.

## Примечание по локальному S3

Документ стека требует MinIO. Для локального контура зафиксирован последний security-релиз community-ветки. Репозиторий MinIO архивирован, поэтому перед production-пилотом этот компонент нужно отдельно пересмотреть: сохранить S3-контракт приложения и выбрать поддерживаемое совместимое хранилище либо управляемый S3.
