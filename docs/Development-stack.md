# Стек разработки «ДомДело» для MAX

Статус документа: рекомендуемый стек для MVP хакатона.  
Актуальность платформенной части: 23.09.2026.

## 1. Исходные требования

Стек выбран с учетом концепции «ДомДело» и требований кейса «Умный город»:

- основной пользовательский сценарий должен полностью работать в MAX;
- решение должно быть доступно в мобильной и веб-версии MAX;
- мини-приложение может работать только как часть чат-бота;
- для MAX рекомендованы JavaScript и React;
- мини-приложение должно быть доступно по HTTPS;
- рабочие токены, пароли и ключи нельзя хранить в репозитории;
- тестовые и смоделированные данные необходимо явно обозначить;
- проект должен воспроизводимо запускаться через Docker одной командой;
- версии зависимостей должны быть зафиксированы;
- при наличии собственного API нужны OpenAPI 3.0/3.1, тестовые данные и `DATA-API.yaml`;
- особое значение имеют стабильность, обработка ошибок, прозрачная архитектура и понятный сценарий проверки.

Основание: `docs/Умный город.pdf`, страницы 6-10, 13, 15 и 18.

## 2. Главное техническое решение

Для MVP рекомендуется **модульный монолит на TypeScript**, а не набор микросервисов.

В одном репозитории находятся:

1. чат-бот MAX;
2. backend и REST API;
3. фоновая обработка уведомлений;
4. React-мини-приложение для жителей и диспетчера;
5. общие типы и схемы данных.

Такой вариант уменьшает время разработки и сборки, упрощает Docker-запуск и при этом позволяет разделить код по предметным модулям. Выделение отдельных сервисов имеет смысл только после пилота и появления подтвержденной нагрузки.

## 3. Рекомендуемый стек

| Слой | Технологии | Назначение |
|---|---|---|
| Язык | TypeScript, Node.js LTS | Один язык для бота, backend и frontend; меньше расхождений между контрактами |
| Менеджер пакетов | pnpm с зафиксированным lock-файлом | Быстрая и воспроизводимая установка зависимостей |
| Чат-бот MAX | `@maxhub/max-bot-api`, Fastify Webhook | Официальный клиент и типы MAX, получение событий, callback-кнопки, сообщения и уведомления |
| Backend | Fastify, TypeBox/JSON Schema | Быстрый HTTP-сервер, проверка входных данных и единые схемы API |
| API-документация | `@fastify/swagger`, OpenAPI 3.1 | Воспроизводимая техническая проверка собственного API |
| Мини-приложение | React, Vite, React Router | Интерфейсы жителя и диспетчера |
| UI MAX | `@maxhub/max-ui` | Компоненты, темы и визуальный стиль MAX |
| Интеграция мини-приложения | MAX Bridge (`max-web-app.js`) | Данные запуска, платформа, диплинки и функции клиента MAX |
| Работа с серверными данными | TanStack Query | Загрузка, кэширование и повтор запросов с понятными состояниями загрузки и ошибок |
| База данных | PostgreSQL 17+ | Пользователи, дома, дела, статусы, подтверждения, роли и журнал событий |
| Доступ к БД | Drizzle ORM + SQL migrations | Типизированные запросы и контролируемые миграции без тяжелого слоя абстракции |
| Поиск дублей | PostgreSQL `pg_trgm` + детерминированные правила | Поиск похожих проблем по дому, месту, категории, времени и тексту без отдельной векторной БД |
| Файлы и фотографии | S3-совместимое объектное хранилище; MinIO локально | Хранение доказательств и фотографий результата вне базы данных |
| Фоновые задачи | Таблица outbox в PostgreSQL + worker в приложении | Надежные уведомления и повторные попытки без обязательного Redis |
| Логи | Pino, JSON-логи, `request_id`/`case_id` | Поиск ошибок и восстановление цепочки действий |
| Тесты | Vitest, Fastify `inject`, React Testing Library, Playwright | Unit-, API-, компонентные и сквозные проверки |
| Контейнеризация | Docker, multi-stage Dockerfile, Compose | Одна команда для запуска всех локальных компонентов |
| HTTPS | Caddy или Nginx на публичном стенде | TLS для webhook и мини-приложения |
| CI | GitHub Actions или CI используемого Git-сервиса | Проверка типов, lint, тесты и Docker-сборка для каждого commit hash |

Полные patch-версии Node.js и npm-пакетов необходимо закрепить в `.nvmrc`, `package.json`, `pnpm-lock.yaml` и Docker-образах после первой успешной интеграционной сборки.

## 4. Компоненты решения

### 4.1. Чат-бот MAX

Задачи бота:

- начать создание дела;
- принять текст и фотографию;
- уточнить дом, подъезд, место и категорию проблемы;
- показать найденное похожее дело;
- обработать «У меня тоже», «Следить» и подтверждение результата;
- отправлять изменения статуса;
- открывать карточку дела в мини-приложении через диплинк.

Для production и демонстрационного стенда следует принимать Webhook в Fastify. Официальную библиотеку MAX следует использовать как клиент исходящих вызовов и источник платформенных типов. Long Polling можно оставить только для краткой локальной отладки.

Технические требования интеграции:

- endpoint webhook доступен по HTTPS на порту 443;
- заголовок `X-Max-Bot-Api-Secret` проверяется до обработки события;
- бот быстро возвращает `200 OK`, а длительная обработка выполняется после сохранения события;
- каждое событие имеет защиту от повторной обработки;
- токен передается MAX API только через заголовок `Authorization`;
- базовый адрес MAX API хранится в конфигурации, а не размазан по коду;
- перед разработкой и перед сдачей проверяется changelog MAX.

На дату подготовки документа официальный адрес API — `https://platform-api2.max.ru`. Его необходимо повторно проверить перед сдачей.

### 4.2. Backend и предметные модули

Рекомендуемые модули:

- `auth` — проверка данных запуска MAX и выдача серверной сессии;
- `users` — пользователи и роли;
- `houses` — дома, подъезды и привязка чатов;
- `cases` — создание и чтение дел;
- `case-workflow` — разрешенные переходы статусов;
- `deduplication` — поиск похожих дел;
- `routing` — определение ответственного по проверяемым правилам;
- `attachments` — фотографии и метаданные файлов;
- `notifications` — сообщения в MAX и повторные попытки;
- `audit` — неизменяемый журнал значимых действий;
- `demo-data` — явно помеченные данные демонстрационного дома.

Статусы дела необходимо реализовать как явную конечную модель состояний, например:

```text
draft
-> registered
-> assigned
-> in_progress
-> awaiting_resident_verification
-> resolved

awaiting_resident_verification
-> disputed
-> assigned
```

Переход статуса выполняется только через единый сервис, который одновременно:

1. проверяет роль и допустимость перехода;
2. меняет состояние дела в транзакции;
3. добавляет запись в журнал событий;
4. создает outbox-событие для уведомления MAX.

### 4.3. Поиск дублей

Для MVP не нужна отдельная ML-модель или векторная база. Достаточно объяснимого алгоритма:

1. отфильтровать открытые дела по дому;
2. сузить выборку по подъезду/месту, категории и временному окну;
3. сравнить нормализованный текст через `pg_trgm`;
4. показать пользователю 1-3 кандидата;
5. окончательное решение принимает пользователь кнопкой «Это та же проблема» или «Создать новое дело».

Такой механизм легче продемонстрировать и проверить. LLM допустима только как необязательный помощник для классификации или черновика описания. Она не должна самостоятельно определять официальный порядок действий или ответственного.

### 4.4. Мини-приложение

Один React-проект обслуживает две роли:

- житель видит список, карточку, историю, фотографии и подтверждение результата;
- диспетчер видит очередь, назначение исполнителя, смену статуса и загрузку результата.

Роль определяется на сервере, а не из параметра URL. Данные `window.WebApp.initDataUnsafe` можно использовать для отображения, но нельзя считать доказательством личности. Сервер должен валидировать исходную строку `window.WebApp.initData` по алгоритму MAX и проверять срок `auth_date`.

Обязательные состояния интерфейса:

- загрузка;
- пустой список;
- успешное действие;
- ошибка с возможностью повторить запрос;
- отсутствие прав;
- потеря сети и восстановление;
- устаревшая версия карточки при одновременном изменении статуса.

Минимальные таблицы PostgreSQL:

Для демонстрационных данных у каждой сущности рекомендуется поле или отдельный набор данных, позволяющий однозначно показать, что сведения смоделированы. Реальные персональные данные в seed-файлах не используются.

## 6. Безопасность

Обязательный минимум:

- секреты находятся только в переменных окружения или секрет-хранилище;
- в репозитории хранится только `.env.example` с пустыми значениями;
- `BOT_TOKEN` никогда не передается во frontend;
- проверяется подпись и возраст `initData` мини-приложения;
- проверяется `X-Max-Bot-Api-Secret` webhook;
- на всех изменяющих маршрутах проверяются роль и принадлежность к дому;
- загружаемые файлы проверяются по MIME-типу, размеру и расширению;
- публичные ссылки на фотографии ограничены по времени;
- чувствительные данные не попадают в логи;
- SQL выполняется только через параметризованные запросы ORM;
- для изменяющих запросов используются idempotency key или защита от повторной обработки;
- зависимости проверяются на известные уязвимости;
- в Docker-контейнере приложение запускается не от `root`.

## 7. Docker и окружения

### Локальный состав `compose.yaml`

- `app` — bot, backend API и worker;
- `web` — собранное React-приложение и reverse proxy;
- `postgres` — основная база данных;
- `minio` — локальное S3-совместимое хранилище;
- `minio-init` — создание bucket при первом запуске.

Redis, Kafka, Kubernetes и отдельный API Gateway в MVP не нужны.

Ожидаемая команда запуска:

```bash
docker compose up --build
```

В репозитории должны быть:

- `Dockerfile` с multi-stage сборкой;
- `compose.yaml`;
- `.dockerignore`;
- `.env.example`;
- `pnpm-lock.yaml`;
- миграции БД;
- seed демонстрационного дома;
- health endpoints `/health/live` и `/health/ready`.

Локальный Docker-запуск не заменяет публичный стенд: для проверки в MAX бот, webhook и мини-приложение должны оставаться доступны по HTTPS.

## 11. Что входит в MVP, а что следует отложить

### Входит в MVP

- полный путь от сообщения до подтвержденного результата;
- роли жителя и диспетчера;
- загрузка фотографий;
- дедупликация по объяснимым правилам;
- явная модель статусов;
- журнал событий;
- уведомления MAX с повторными попытками;
- демонстрационные данные одного дома;
- Docker-запуск и документация проверки.

### После MVP

- реальные интеграции с ГИС ЖКХ, УК и муниципальными системами;
- продвинутая аналитика;
- полнотекстовая или семантическая ML-дедупликация;
- сложная оркестрация нескольких исполнителей;
- отдельные микросервисы;
- Kubernetes;
- LLM в критическом контуре принятия решений.

## 12. Критерий готовности технического MVP

MVP считается технически готовым, если:

1. два пользователя в MAX создают сообщения об одной проблеме;
2. бот предлагает объединение и создает одно коллективное дело;
3. диспетчер меняет статус в мини-приложении;
4. жители получают уведомление в MAX;
5. исполнитель прикладывает фотографию результата;
6. житель подтверждает или оспаривает результат;
7. повторный webhook не создает дубль;
8. после ошибочного действия пользователь может продолжить сценарий;
9. сценарий проходит в мобильной и веб-версии MAX;
10. чистый клон запускается через Docker по README;
11. OpenAPI, тестовые данные и `DATA-API.yaml` соответствуют фактическому API;
12. в репозитории и логах нет рабочих секретов.
