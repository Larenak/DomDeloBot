# Регистрация и права доступа

Вход выполняется через мини-приложение MAX. Сервер проверяет подпись `initData` и создаёт учётную запись с базовой ролью жильца.

## Житель

Житель выбирает существующий дом из подсказок адресов. Сервер повторно проверяет код дома по ГАР и добавляет адрес в его профиль. Личный код и проверка проживания для этого шага не требуются. После добавления дом становится текущим: доступны просмотр дел и обычные действия жильца. Можно добавить несколько адресов, переключаться между ними и удалить любой в разделе «Мои дома».

Адрес из подсказок подтверждает существование дома, но **не доказывает проживание**. Любой пользователь MAX может добавить доступный адрес и пользоваться возможностями жильца в этом доме. Это сознательное правило открытого доступа; не размещайте в делах сведения, которые должны видеть только проверенные жители.

При удалении адрес исчезает из профиля и доступ к нему прекращается. Если удалён текущий адрес, приложение выбирает другой сохранённый дом. При удалении последнего адреса снова открывается экран добавления дома. Созданные ранее дела не удаляются. Служебное назначение для удалённого дома отзывается; повторное добавление адреса даёт только роль жильца.

## Диспетчер и исполнитель

Служебные роли по-прежнему требуют личного приглашения. Уполномоченный оператор проверяет полномочия сотрудника вне приложения и выпускает код для конкретного MAX ID, дома и роли. Код действует 72 часа, используется один раз и хранится в базе только как SHA-256 хеш. Публичного API выдачи кодов нет.

Человек должен один раз открыть мини-приложение через MAX. Оператор узнаёт его MAX ID с формы служебного приглашения, а UUID рабочего дома — из таблицы `houses` (`SELECT id, address FROM houses WHERE is_demo = false`). Для выдачи нужен доступ к окружению приложения и базе данных.

В Docker Compose:

```powershell
docker compose exec app node apps/server/dist/db/issue-house-invite.js --house-id <UUID_ДОМА> --max-user-id <MAX_ID> --role dispatcher --verified
```

При запуске сервера без Docker:

```powershell
pnpm --filter @domdelo/server invite:house --house-id <UUID_ДОМА> --max-user-id <MAX_ID> --role dispatcher --verified
```

Для исполнителя используйте `--role executor`. Код передают лично. Флаг `--verified` означает, что оператор уже проверил основание для назначения по доверенному источнику. Сервер сопоставляет код с подтверждённой MAX-учётной записью и при каждом запросе заново проверяет действующее назначение в `house_role_grants`. Отозванное назначение не сохраняется в старой сессии.

## Группа дома и представитель УК

Для реального дома оператор сначала проверяет адрес, владельца группы и полномочия УК вне ДомДела. Бота добавляют в **групповой чат MAX** с правами отправки сообщений, чтения участников, `read_all_messages`, `pin_message` и `add_remove_members`. Затем применяют миграции и привязывают чат:

```powershell
pnpm db:migrate
pnpm --filter @domdelo/server house:chat bind --house-id <UUID_ДОМА> --chat-id <MAX_CHAT_ID> --verified
```

Код `--verified` означает, что оператор сверил дом и право привязать этот чат. Бот проверяет, что чат существует и сам участвует в нём. После привязки новые дела и изменения их статуса публикуются только в чатах соответствующего дома с адресом и номером дела. Если чат не привязан, уведомление остаётся в очереди до исправления настройки.

Отдельный **служебный** MAX-аккаунт УК задаётся после проверки организации и её представителя:

```powershell
pnpm --filter @domdelo/server house:chat management --house-id <UUID_ДОМА> --uk-name "УК Пример" --service-max-user-id <MAX_USER_ID> --verified
```

При подтверждённой смене УК ту же команду выполняют с новым названием и служебным MAX ID. Скрипт немедленно отзывает прежние права этого аккаунта в доме. Фоновая задача в течение минуты проверяет его членство в привязанных группах, удаляет только ранее указанный служебный аккаунт и сообщает о новой УК, когда её аккаунт уже вступил. Для подтверждённого отсутствия УК используют `house:chat management --house-id <UUID_ДОМА> --none --verified`. При отсутствии представителя бот сообщает об этом и пытается закрепить сообщение; отсутствие права `pin_message` не мешает отправке. Далее членство перепроверяется не реже раза в сутки при работающем сервере. Повторные сообщения при неизменном отсутствии не отправляются.

Не указывайте личный аккаунт жильца как служебный аккаунт УК: при смене организации он может быть удалён из группы. Данные об УК в разделе услуг взяты из датированного справочного среза и не используются для автоматического удаления участников. Если у бота нет права `add_remove_members`, удаление повторится на следующей проверке после выдачи права. Настройка пилотного дома и реальные сообщения в MAX требуют отдельной проверки с ботом и группой.

На бесплатном web-плане Render фоновый таймер может не работать, пока сервис спит. Для гарантированной ежедневной проверки нужен постоянно работающий сервер или внешний планировщик, который запускает задачу; текущая конфигурация `render.yaml` этого не гарантирует. Изменения в реестре УК не определяются автоматически: оператор вносит подтверждённую смену командой выше.
